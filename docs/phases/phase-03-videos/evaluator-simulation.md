## 4. Causes behind step 2

1. **Code defect — fixed (`f809631`).** `scripts/verify-large-upload.ts` (Gate 3, `9821dfb`) was inside the production build, so a fresh `npm run build` emitted `dist/src/main.js` instead of `dist/main.js`; the API and the worker could not start on a clean clone. The main environment hid it because its `dist/` had been built before the script existed and was never rebuilt. Fix: `scripts` excluded in `tsconfig.build.json` (the script still type-checks through `tsconfig.json` and runs through ts-node).
2. **Host I/O slowdown — not a code change.** Loading `@nestjs/core`, `typeorm` and `@aws-sdk/client-s3` took **357 s in the main environment's own API container** and 247 s in the clone's, while the main API had started in 19 s the night before. Docker Desktop's bind-mount I/O was degraded host-wide during this run (the disk was 94 % full; Defender real-time protection on; its exclusions could not be read without administrator rights). The setup's health window (24 × 5 s) is shorter than such a start, so the setup stops with a visible FAIL instead of waiting. Restarting Docker Desktop would interrupt the main environment, which this checkpoint forbids, so the cause was not isolated further.

No timeout, health window or test was changed to make the run pass.

## 7. Operational note

Every Compose command for a second copy must carry the same `COMPOSE_PROJECT_NAME` and `STREAMTUBE_*_PORT` values. During this run one `docker compose up -d worker` was issued without the port variables; Compose tried to recreate the clone's `db` and `minio` on the default ports and stopped on "port 5432 is already allocated". The main environment was not affected (different project; the bind failed), the clone's data survived (4/4 migrations, both buckets), and the clone was brought back with the right variables.
