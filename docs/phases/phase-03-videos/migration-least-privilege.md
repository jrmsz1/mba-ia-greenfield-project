## 2. Credential delivery — decided (TD-16, TD-15 "evaluator setup" revisions)

`nestjs-api` and `worker` bind-mount the whole `nestjs-project/` directory, and both processes load `nestjs-project/.env` with dotenv, so any secret placed in that file would reach both containers. The decision recorded on 2026-11-12 (Decision A unchanged) removes every credential from the mounted `.env` and delivers them through one Compose `env_file` per process role, generated by the setup scripts in `<repo>/.local/secrets/` — a directory inside the checkout but git-ignored and outside every bind mount — with owner-only permissions, never overwritten silently and never printed:

| File | Contents | Consumed by |
|---|---|---|
| `minio.env` | `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` (the **existing** root pair is reused, so the `minio-data` volume stays usable) | `minio` |
| `api.env` | `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` of the API identity, `S3_DELIVERY_*` | `nestjs-api` |
| `worker.env` | `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` of the worker identity | `worker` |
| `test-api.env` | `S3_TEST_API_*`, `S3_TEST_WORKER_*`, `S3_TEST_DELIVERY_*` (multi-role suites) | ephemeral `test-api` (`compose.test.yaml`, `run --rm`) |
| `test-worker.env` | the same three test identities | ephemeral `test-worker` (`compose.test.yaml`, `run --rm`) |
| `provision.env` | root, `S3_API_*`, `S3_WORKER_*`, `S3_DELIVERY_*`, the test identities, `S3_TEST_MAINTENANCE_*` | on-demand provisioning container (not a Compose service) |
| `maintenance.env` | `S3_TEST_MAINTENANCE_*` + test-database lock access | on-demand maintenance container (not a Compose service) |

Consequences: the operational API never receives root, maintenance or test credentials; the operational worker never receives root, delivery, maintenance or test credentials; the test containers receive only the three restricted test identities (no root, no production identity, no maintenance credential); nothing is required in the shell and there is no fallback to root or to production identities. Integration, e2e and media suites no longer run through `docker compose exec nestjs-api`/`worker` (they fail closed there by design) but in the ephemeral `test-api`/`test-worker` containers, which use only `DB_TEST_NAME`, `S3_TEST_BUCKET` and `PGBOSS_TEST_SCHEMA`, run finite commands with no restart, and never reach the operational API or share jobs with the operational worker.

## 4. Exact migration sequence (CP2 — to apply only after approval)

Prepared at CP1 (read-only for the running stack): `./scripts/setup.sh --prepare-only` already generated `<repo>/.local/secrets/*.env` in the main checkout — git-ignored, outside the bind mount, owner-only ACL — with `minio.env` holding the **existing** MinIO root pair copied from `.env`; the read-only provisioning preflight (`PROVISION_MODE=check`) against the main MinIO answered "no conflicting bucket, policy or identity; nothing written". `docker compose --dry-run up -d` on the main project shows that **only `nestjs-api` and `worker` would be recreated**; `db`, `mailpit` and `minio` keep running (the MinIO environment resolves to the same values, so neither the anonymous PostgreSQL volume nor `minio-data` is touched).

0. **Freeze:** no test run in progress (the test-run advisory lock is free); record the inventory of §1 (buckets/objects/sessions/users/policies, databases) and `sha256sum` of `nestjs-project/.env` and of the credential files.
1. **Run the setup** in the main checkout: `./scripts/setup.sh` (or `.\scripts\setup.ps1`). It keeps every credential file, moves the four legacy credential lines (`MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`) out of `.env` into an owner-only backup under `.local/secrets/` (comment markers left in `.env`), validates Compose, provisions (creates the 7 policies and 7 identities; both buckets exist and are kept), builds, applies pending migrations, then recreates `nestjs-api` (now `npm run start:prod`) and starts `worker`.
2. **Re-run the setup once** → nothing created (idempotency), credential files unchanged.
3. **Post-checks:** `./scripts/verify.sh` — health, effective environment of every container by variable name (API: API + delivery identity only; worker: worker identity only; test containers: the three test identities only; mounted `.env`: no credential), Git hygiene, essential suites.
4. **Inventory (after):** identical buckets, object counts and the **47** sessions in `streamtube-videos-test`; MinIO users 7, custom policies 7; databases unchanged (`streamtube`, `streamtube_backup_verify`, `streamtube_test`, `postgres`); the dump untouched.
5. **No cleanup:** the 47 abandoned sessions and every object are preserved; the maintenance wrapper is not run.
6. **Regression and gates (CP2 evidence):** `./scripts/verify.sh --full`, the permission matrix, then re-validation of Gates 2, 4, 5, 6, 7, 8 and the reconciler suite with new evidence; `progress.md` only with what was executed.

**Recovery (no silent root fallback):** if step 1–3 fails, (a) restore `nestjs-project/.env` from the owner-only backup in `.local/secrets/` and the previous `compose.yaml` from Git (`git checkout <commit before CP1> -- nestjs-project/compose.yaml`), then `docker compose up -d --force-recreate nestjs-api` — an explicit, visible rollback to the pre-migration configuration; (b) the provisioned users/policies are additive and may stay (nothing to undo); (c) the code has no fallback: the API/worker refuse to start without their own identity and refuse `MINIO_ROOT_*`, so a half-applied state fails closed instead of silently using root. No step writes or deletes objects or databases.
