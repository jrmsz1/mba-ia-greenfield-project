## 2. Credential delivery — decided (TD-16, TD-15 "evaluator setup" revisions)

`nestjs-api` and `worker` bind-mount the whole `nestjs-project/` directory, and both processes load `nestjs-project/.env` with dotenv, so any secret placed in that file would reach both containers. The decision recorded on 2026-11-12 (Decision A unchanged) removes every credential from the mounted `.env` and delivers them through one Compose `env_file` per process role, generated by the setup scripts in `<repo>/.local/secrets/` — a directory inside the checkout but git-ignored and outside every bind mount — with owner-only permissions, never overwritten silently and never printed:

| File | Contents | Consumed by |
|---|---|---|
| `minio.env` | `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` (the **existing** root pair is reused, so the `minio-data` volume stays usable) | `minio` |
| `api.env` | `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` of the API identity, `S3_DELIVERY_*` | `nestjs-api` |
| `worker.env` | `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` of the worker identity | `worker` |
| `test-api.env` | `S3_TEST_API_*`, `S3_TEST_WORKER_*`, `S3_TEST_DELIVERY_*` (multi-role suites) | ephemeral `test-api` (`compose.test.yaml`, `run --rm`) |
| `test-worker.env` | the same three test identities | ephemeral `test-worker` (`compose.test.yaml`, `run --rm`) |
| `provision.env` | root, `S3_API_*`, `S3_WORKER_*`, `S3_DELIVERY_*`, the test identities, `S3_TEST_MAINTENANCE_*` | on-demand provisioning container (not a Compose service) |
| `maintenance.env` | `S3_TEST_MAINTENANCE_*` + test-database lock access | on-demand maintenance container (not a Compose service) |

Consequences: the operational API never receives root, maintenance or test credentials; the operational worker never receives root, delivery, maintenance or test credentials; the test containers receive only the three restricted test identities (no root, no production identity, no maintenance credential); nothing is required in the shell and there is no fallback to root or to production identities. Integration, e2e and media suites no longer run through `docker compose exec nestjs-api`/`worker` (they fail closed there by design) but in the ephemeral `test-api`/`test-worker` containers, which use only `DB_TEST_NAME`, `S3_TEST_BUCKET` and `PGBOSS_TEST_SCHEMA`, run finite commands with no restart, and never reach the operational API or share jobs with the operational worker.

## 4. Exact migration sequence (to apply only after approval)

0. **Freeze:** no test run in progress (the test-run advisory lock is free); stop `nestjs-api` (`docker compose stop nestjs-api`); `worker` is already stopped.
1. **Inventory (before):** re-run §1 and keep the output.
2. **Secrets:** the setup script generates the seven identities' secrets (API, worker, delivery; test API, test worker, test delivery; test maintenance) into the files of §2 under `<repo>/.local/secrets/`, reusing the existing MinIO root pair in `minio.env`; IDs distinct, none equal to `MINIO_ROOT_USER`; existing files are never overwritten silently; nothing is written to tracked files and no value is printed.
3. **Preflight:** run the provisioning container with `PROVISION_MODE=check` against `minio` (expected: OK; buckets exist and are kept; no user/policy conflict).
4. **Provision:** run it in apply mode → creates the 7 policies and the 7 identities; both buckets are **kept as is** (no `mc mb`, no delete). Re-run once → nothing created (idempotency).
5. **Compose/config switch** (§5): `compose.yaml` references `minio.env`, `api.env` and `worker.env` as required `env_file` entries; `compose.test.yaml` adds the profile-gated `test-api`/`test-worker` services with `test-api.env`/`test-worker.env`; the credentials are removed from the mounted `.env`; `.env.example` lists the credential names only as comments pointing to the generated files.
6. **Recreate** `minio` only if its environment source changed (data volume untouched), then `nestjs-api` (and `worker` when used). The API fails fast if its bucket check (HeadBucket) or credential validation fails — **no fallback to root**.
7. **Post-checks:** `docker compose config --no-env-resolution` (never plain `config`, which would print values) shows each `env_file` only on its service; the effective environment of `nestjs-api` has no `MINIO_ROOT_*`, `S3_TEST_MAINTENANCE_*` or `S3_TEST_*`, that of `worker` additionally no `S3_DELIVERY_*`; the mounted `.env` holds no credential; the API boots (HeadBucket OK); a `test-api` container shows only the three test identities.
8. **Inventory (after):** buckets, object counts and sizes identical to step 1 (users: 7, policies: 7 custom); databases unchanged, `streamtube_backup_verify` and the dump untouched.
9. **No cleanup:** the 47 abandoned multipart sessions in `streamtube-videos-test` and every object in both buckets are **preserved**; the maintenance container is not run as part of the migration (any later cleanup is a separate, explicit request).
10. **Regression on the main environment:** permission matrix, `npm test` and `npm run test:e2e` in `test-api`, `npm run test:media` in `test-worker` (all through `docker compose -f compose.yaml -f compose.test.yaml run --rm …`); then re-validate Gates 2, 4, 5, 6, 7, 8 and the reconciler suite with new evidence (they stay as they are until then).

**Recovery (no silent root fallback):** if step 4–7 fails, restore the previous `.env`/`compose.yaml` from step 1's backup and recreate the services — that is an explicit, visible rollback to the pre-migration configuration, never an automatic fallback in code (the code has none: API/worker refuse to start without their own identity). Provisioned users/policies are additive and may stay; nothing is deleted. Data is never at risk: no step writes or deletes objects (except the optional, guarded step 9 on the test bucket only).
